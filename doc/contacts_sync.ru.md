# Синхронизация контактов BSN Expert

Руководство для разработчиков приложений, которые хотят синхронизировать адресную книгу с BSN.Expert.

## Авторизация

- Получение ключа описано в [api.ru.md](/doc/api.ru.md).
- Заголовок: `Authorization: Bearer <API_KEY>`.
- Используйте ключ с разрешениями на «Контакты». Проверка прав идёт по действиям: `read`, `create`, `update`, `delete`.

## Эндпоинт

- `POST /api/contacts/sync`
- Формат: `application/json`

## CORS

- Эндпоинт доступен с любого origin (`Access-Control-Allow-Origin: *`).
- Preflight-запрос `OPTIONS /api/contacts/sync` не требует авторизации и возвращает `204 No Content`.
- Разрешены метод `POST` и заголовки `Authorization`, `Content-Type`.

## Поля запроса

```json
{
  "current_timestamp": 1717230000000,
  "cursor": null,
  "items": {
    "G...ADDRESS1": { "label": "Имя", "updated_at": 1717220000000 },
    "G...ADDRESS2": { "label": null,  "updated_at": 1717210000000 }
  }
}
```

- `current_timestamp` — обязательный, Unix время в миллисекундах. Если расхождение больше 5 000 мс, запрос отклоняется.
- `cursor` — последняя полностью применённая клиентом метка `next_cursor`. Для первой синхронизации передайте `null`.
- `items` — опциональный объект изменённых контактов, описанный ниже.


## Структура контактов

Контакты представляют собой элементы объекта, где ключ — это корректный Stellar-адрес (G...), а значение — объект с:
  - `label`: строка или `null`, где отсутствие имени это пустая строка, а `null` означает удаление контакта,
  - `updated_at`: целое число (мс с эпохи), момент последнего изменения контакта.

## Логика клиента

1. Для первой синхронизации отправьте `cursor: null`.
2. Сервер вернёт изменения и `next_cursor`.
3. Примените все изменения локально и только после успешного применения сохраните `next_cursor`.
4. В следующем запросе передайте сохранённое значение как `cursor`.
5. Если запрос или ответ потерялся, повторите запрос с прежним `cursor`: сервер повторно вернёт ещё не подтверждённые изменения.

Не запускайте несколько синхронизаций параллельно для одного локального хранилища: применяйте ответы и сохраняйте `next_cursor` последовательно. Разные устройства могут использовать собственные cursor с одним API-ключом.

Поле `cursor` можно не передавать только для совместимости со старыми клиентами. В этом режиме сервер хранит общую метку на API-ключе, поэтому надёжный повтор после потерянного ответа не гарантируется.

В `items` клиент отправляет контакты, изменившиеся после предыдущей синхронизации. `updated_at` разрешает конфликты между версиями контакта, но не используется как cursor доставки.

## Логика сервера

1. Загрузка текущих контактов клиента.
2. Сравнение с присланными данными:
   - Добавить, если у клиента есть label и его `updated_at` новее, а на сервере нет записи или label был пуст.
   - Обновить, если label отличается и клиентский `updated_at` новее.
   - Удалить, если у клиента `label=null`, на сервере было имя, и метка обновления новее.
   - Соответствующие действия выполняются только если у ключа есть соответствующие разрешения (`create`/`update`/`delete`).
3. При разрешении `read` сервер вернёт контакты, чья серверная revision новее переданного `cursor`.

## Ответ
```json
{
  "status": "OK",
  "next_cursor": 42,
  "report": {
    "errors": [],
    "permissions": { "read": true, "create": true, "update": true, "delete": false },
    "added": ["G..."],
    "not_added": [],
    "updated": [],
    "not_updated": [],
    "deleted": [],
    "not_deleted": []
  },
  "items": {
    "G...ADDRESS3": { "label": "Новое имя", "updated_at": 1717235000000 }
  }
}
```
- `report` — что удалось/не удалось применить с учётом прав.
- `next_cursor` — revision снимка, из которого сформирован ответ. Сохраните её только после успешного применения `items`.
- `items` — присутствует только при `read=true`; содержит изменения новее переданного `cursor`.

Коды ответа:
- 200 — успех.
- 400 — проблемы формата (`JSON`, `current_timestamp`, `cursor`, `items`).
- 401 — отсутствует/неверный ключ.
- 403 — нет нужных прав.
- 409 — переданный `cursor` новее текущей серверной revision либо контакты непрерывно менялись во время обработки. В первом случае требуется полная синхронизация с `cursor: null`, во втором — повтор запроса.

## Пример cURL
```bash
CURRENT_TIMESTAMP_MS="$(($(date +%s) * 1000))"

curl -X POST https://bsn.expert/api/contacts/sync \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  --data-binary @- <<JSON
{
  "current_timestamp": $CURRENT_TIMESTAMP_MS,
  "cursor": null,
  "items": {
    "GAAAA...1": { "label": "Alice", "updated_at": 1717220000000 },
    "GBBBB...2": { "label": null, "updated_at": 1717210000000 }
  }
}
JSON
```

## Замечания по времени
- Клиенту важно отправлять точное время в мс; держите синхронизацию часов (NTP) или поправки на сетевые лаги.
- Все сравнения ведутся в мс Unix time. Если хотите переиспользовать серверные метки, берите `updated_at` из ответа и сохраняйте на клиенте.
